# Оффлайн-инструменты (`app/agents/`)

Набор **оффлайн** инструментов, дёргающих LLM (сейчас DeepSeek API) для задач
вокруг словаря. Растущий каталог: добавляются новые инструменты по мере надобности.

**Область:** только оффлайн — разовая/пакетная обработка, подготовка данных,
в будущем — инструменты разработки (агентский цикл, тесты, оркестрация).
**НЕ рантайм.** Ничто отсюда не обслуживает живые запросы пользователей.
Рантайм-классификация (запрос пользователя, новые слова) — отдельная история,
здесь её нет.

Не «агенты» в смысле автономности (ранняя идея архитектор/исполнитель +
`Dockerfile.agent` отвергнута). Пока — скрипты с чёткими режимами, запускаемые
вручную. Автономный/агентский цикл — возможное будущее (см. «Развитие»).

---

## Общие конвенции (для ВСЕХ инструментов)

Любой новый инструмент здесь следует этим правилам — так каталог остаётся
единообразным и предсказуемым.

**Запуск.** Внутри контейнера `punzh_django` (нужен доступ к БД и Django),
рабочий каталог `-w /app/agents` (чтобы `load_env` нашёл `.env` рядом):
```bash
docker exec --user 1000:1000 -w /app/agents punzh_django python <tool>.py [флаги]
```

**Окружение.** `openai` ставится в контейнер РАЗОВО
(`docker exec punzh_django pip install openai`); в прод-requirements НЕ входит —
это dev-инструменты. При пересборке образа ставить снова.

**Секреты.** `.env` (рядом со скриптами) содержит `DEEPSEEK_API_KEY=sk-...`
**без кавычек** (кавычки → 401; `load_env` их не снимает). `.env` в `.gitignore`.

**Bootstrap Django.** Скрипт делает `load_env()`, добавляет `/app` в `sys.path`
(проект лежит там, а рабочий каталог — `agents/`), затем `django.setup()`
с `DJANGO_SETTINGS_MODULE=punzh.settings`.

**Данные.** Все рабочие json — в `data/` (в `.gitignore`). Ценные артефакты
(напр. замороженная онтология) коммитятся ОТДЕЛЬНО в осмысленное место репо
(`dict/fixtures/custom/`), не из `data/`.

**LLM-вызовы.** Просить строгий JSON, парсить устойчиво (срезать markdown-
обёртки, `try/except` на битый ответ — пропускать с логом, не падать).
Долгие пакетные прогоны — с автодокатом (продолжение с места обрыва) и
периодическим сохранением. Стоимость мизерна (кэш DeepSeek ловит постоянный
префикс промпта).

**Заливка в БД — НЕ здесь.** Инструменты пишут json; заливкой в модели
занимаются штатные management-команды в `dict/` (`load_semantic_*`,
`load_keywords`). Разделение: agents/ готовит данные, dict/ пишет в БД.

## Каталог инструментов

### Данные словаря

#### `build_ontology.py` — онтология смысловых полей + классификация
Три режима (подробности внутри файла и в `docs/CONCEPT_ai_search.md`):
- `--design-only --runs N --sample K` — N прогонов проектирования онтологии
  (ансамбль; выборки не пересекаются; служебные части речи исключены).
- `--consolidate FILE` — усушка N наборов в единый список (объединить
  синонимы, исключить функционально-грамматические поля). Итог вычитывается
  человеком и замораживается.
- `--ontology FROZEN --limit N` — классификация статей по замороженной
  онтологии (1-3 поля, `no_field` валиден, новые поля запрещены). Автодокат +
  сохранение каждые 100. Возвращает и `keywords`.

Проверка подключения к DeepSeek: `probe_deepseek.py`.

#### (план) извлечение иллюстраций
Структурировать примеры употребления (карельский ↔ русский перевод) из
`article_html` — сейчас блокер (нет маркеров). Кандидат на LLM-инструмент.

#### (план) эмбеддинги
Векторы русских частей статей для семантического rerank (этап 2 AI-поиска).

### Разработка (возможное будущее)

Инструменты для агентского цикла разработки: генерация/правка кода по задаче,
запуск тестов, оркестрация шагов. Пока не реализовано. При появлении — те же
общие конвенции (окружение, .env, устойчивый парсинг), отдельные скрипты.

## Как добавить новый инструмент

1. Один скрипт `<tool>.py` в `app/agents/`, с чёткими режимами-флагами.
   Имя не `test_*.py` (иначе `manage.py test` примет его за юнит-тест).
2. Следовать общим конвенциям выше (запуск, bootstrap, data/, JSON, автодокат
   для долгих прогонов).
3. Переиспользовать общее: `load_env`; при росте вынести обёртку клиента
   DeepSeek (ключ/base_url/retry/парсинг) в общий модуль (напр.
   `deepseek_client.py`), чтобы инструменты не дублировали инициализацию.
4. Заливку результата в БД — отдельной management-командой в `dict/`, не в
   самом инструменте.
5. Дописать раздел в «Каталог» этого файла.

## Общие модули

- `load_env.py` — читает `.env` из текущего каталога в `os.environ`. Запускать
  инструменты с `-w /app/agents`. (Рекомендация: научить снимать кавычки/пробелы —
  `.strip().strip('"').strip("'")` — чтобы не спотыкаться на `.env`.)
- `probe_deepseek.py` — проверка подключения (ключ, соединение, простой запрос). Не называть `test_*.py`: Django подхватит как юнит-тест.
- (план) `deepseek_client.py` — общая обёртка клиента, когда инструментов
  станет больше одного.

## Развитие

- Больше инструментов данных: извлечение иллюстраций, эмбеддинги, проверка
  качества разметки.
- Инструменты разработки: агентский цикл (код + тесты + оркестрация) — если/когда
  понадобится. Сохранять принцип: оффлайн, единые конвенции, заливка в БД
  отдельными командами.

## Что НЕ коммитить

`.env` (ключ!), `data/` (рабочие json), `__pycache__`. Всё в `.gitignore`.
