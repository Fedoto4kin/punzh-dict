## 1. Исправить пропущенные «см.»  
**Проблемы:**

1. В редких случаях «см.» встречается **без тега `<i>`**, авторазметка пропустила.  
2. Иногда авторазметка **не смогла найти целевое слово**.  
3. Проверить, что нигде «см.» не идёт с **латинской c** вместо кириллической «с».

**Решение:**  
Нужен **интерактивный скрипт**, который:

- ищет все случаи «см.» и «ср.» в статьях перед карельским словом;  
- проверяет наличие `<i>`;  
- проверяет корректность ссылки;  
- проверяет, что буква «с» или "p" кириллическая;  
- точка после "см" или "ср" может отсуствовать
- предлагает вручную выбрать целевую статью, если авто‑поиск не справился.

**Главный вопрос:**  
Как искать статью, на которую указывает текущая?

→ Решение: нормализованный поиск по **лемме**, **орфографии**, **вхождению с начала**.

## 3. Очистить переводы  
**Проблема:**  
Переводы сейчас избыточны, потому что раньше не было векторного поиска.  
Пример: статья *hotkoi* содержит множество однотипных переводов:

- быстрый  
- легкий  
- легкий на ход  
- пользующийся  
- пользующийся спросом  
- скорый  
- спросом  
- ход  
- ходкий

Особенно замусорены формы глагола **быть** и **становиться**.

**Задача:**  
Сделать LLM‑очистку переводов (см скрипт app/agents/build_ontology.py, работаем с Deepseek):

- объединить дублирующиеся значения;  
- убрать служебные слова («быть», «становиться»), если они не несут смысл;  
- оставить только семантические ядра;  
- привести к формату полнотекстового поиска.

**Проблема в поиске:**  
Поиск по «быть» не предлагает уточнений → нужно добавить **prio‑фильтр**.

## 6. Вывод размеченных слов по онтологии — сделано (закрытая бета)

Справочник и привязки (`SemanticField`, `ArticleSemanticField`) уже были в БД.
Сделан просмотр: админка + страницы `/ontology/`, `/ontology/<id>/`.
В обычный `/search/` не смешивали. В шапке и на главной ссылки нет — вход только
по прямой ссылке (и из админки).

### 6.1. Админка

- На карточке статьи инлайн смысловых полей **только чтение**, на **добавлении**
  статьи блок скрыт.
- Справочник `SemanticField` целиком read-only (заливка — management-команды).
- Фильтр списка статей по полю; у поля — число статей и ссылка на сайт.

### 6.2. Сайт

- `/ontology/` — список полей с числом статей; `/ontology/<id>/` — карточки
  как в поиске, карельская сортировка, пагинация сверху.
- Неизвестный id → 404; пустое поле → 200 без статей.
- Поиск «найти поле» на индексе **не** делали (полей мало).
- Кеш списка статей **не** вводили (как у `/tags/`).
- URL по числовому id, не slug.

Отсылки без своей разметки («см. X», нет перевода для LLM) **на выдаче**
попадают в поле целевого слова через входящий `ArticleLink`. В БД поле
не копируется. Исходящие «см.» и статьи, у которых уже есть своё поле,
чужое поле не наследуют.

Тесты: `dict/tests/test_ontology_view.py`.

### 6.3. Разметка

Три контура по-прежнему разделены: поля в `ArticleSemanticField`, пометы в
HTML/`ArticleIndexTag`, «см.» в `ArticleLink`. Конвейер авторазметки не меняли.

### 6.4. Dev-скрипты — не делаем

Доразметка новой статьи / дыры — LLM, не отдельные скрипты аудита меток.

## 7. Поля из перевода, не из примера

**Блокер:** §3 «Очистить переводы». Пока ядра переводов грязные, LLM часто
пометит «по переводу» шум. Код схемы/скрипта/заливки можно готовить заранее;
**полный прогон DeepSeek и заливка `from_translation` — только после §3**.

**Проблема:** классификатор смотрел переводы **и** иллюстрации, все привязки
в `ArticleSemanticField` равноправны. У части статей в онтологию попали
смежные смыслы из примеров.

**Решение:** не переклассифицировать поля и не выбирать одно «главное».
На связи — флаг `from_translation` («по переводу»): смысл виден в переводах
леммы, а не только в примере. Несколько True на статью нормальны;
все False — тоже (поля с иллюстраций / модель не уверена).

Отдельный оффлайн-скрипт (`app/agents/pick_translation_fields.py`) отдаёт в
DeepSeek **только переводы** и уже проставленные поля (имя + определение).
Иллюстрации в промпт не идут.

- 0 полей → пропуск;
- иначе DeepSeek, в т.ч. у статьи с одним полем;
- ответ: список имён из переданного набора (можно пустой).

Заливка: `load_translation_fields` обновляет только флаг, связи не
удаляет и не создаёт.

**Не делаем в этой версии:** переклассификация полей; чистка keywords;
снятие «лишних» полей из иллюстраций; фильтр `/ontology/` и AI-поиска по
`from_translation` (статья по-прежнему во всех своих полях).
