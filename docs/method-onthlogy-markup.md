# Разметка онтологии смысловых полей

Как строилась семантическая разметка словаря тверских карельских говоров
А. В. Пунжиной (~15968 статей): цель, средства, решение, загрузка в БД.
Дополняет `ai-search.md` со стороны данных — эта разметка питает группу
«по смысловому полю» в AI-поиске и страницы просмотра `/ontology/`.

---

## 1. Цель

AI-поиску нужна семантическая группировка выдачи (группа «Слова того же
смысла»). Для этого в БД должны появиться две сущности:

1. **справочник смысловых полей** (`SemanticField`) — 20-28 широких категорий;
2. **привязка статья→поле** (`ArticleSemanticField`) — каждая значимая статья
   размечена 1-3 полями.

Разметить ~16k статей руками нельзя, поэтому её строит модель. Ключевое решение:
**развести две подзадачи** — сначала *спроектировать* онтологию, отдельно потом
*классифицировать* по ней статьи. Это операции с разной ценой ошибки: плохая
онтология портит всё, поэтому её оценивают глазами и замораживают до того, как
ею разметят весь словарь.

---

## 2. Средства

**Данные статьи** (вход собирает `build_article_input`):
- переводы — `ArticleIndexTranslate.rus_word`;
- русские фрагменты иллюстраций — кириллица, выдранная из `article_html`
  (`cyrillic_from_html`), минус то, что уже в переводах, обрезано до 15;
- пометы — `Tag` / `ArticleIndexTag` (используются как фильтр).

**Принцип входа: модели даём ТОЛЬКО русский.** Карельское слово (`word`) в
промпт не идёт — модель не знает диалекта, русский перевод для неё
единственная надёжная семантическая опора.

**Модель и режим.** Два канала, один замёрзший промпт:

| | Пакет (~16k) | Одна статья (новое слово) |
|---|---|---|
| Скрипт | `agents/build_ontology.py --ontology` | `manage.py classify_article --id` |
| API | DeepSeek напрямую (`DEEPSEEK_API_KEY` в `agents/.env`) | шлюз Timeweb (`TIMEWEB_AI_*`, модель `TIMEWEB_AI_MODEL_CLASSIFY`) |
| Онтология | JSON-файл (`ontology_frozen.json`) | справочник `SemanticField` в БД |
| Запись | JSON → `load_semantic_*` / `load_keywords` | сразу в `ArticleSemanticField` + `ArticleKeyword` |

Общий текст промпта и сбор входа статьи — `dict.ai.prompts`
(`SYSTEM_PROMPT_FROZEN`, `build_article_input`): пакетный скрипт импортирует
их оттуда, чтобы тексты не разъезжались.

**Инструменты:**
- `build_ontology.py` — оффлайн-движок, три режима (`--design-only`,
  `--consolidate`, `--ontology`);
- `load_semantic_fields`, `load_semantic_classification`, `load_keywords` —
  management-команды заливки пакетного JSON в БД;
- `classify_article --id` — доклассификация одной статьи (см. §5);
- `pick_translation_fields.py` + `load_translation_fields` — отдельный проход:
  какие из уже проставленных полей из **переводов** леммы (`from_translation`),
  не переклассификация (см. §4.1).

Везде `temperature=0` (воспроизводимость) и устойчивый парсинг JSON (срезаем
markdown-обёртки, берём первый объект/массив).

---

## 3. Решение

Конвейер из четырёх шагов: собрать сырые онтологии → усушить в одну →
заморозить и залить справочник → прогнать классификацию по всему словарю.

### 3.1. Сбор онтологии — прогоны и выборка (`--design-only`)

Проектируем не одну онтологию, а **ансамбль черновиков**, чтобы не зависеть от
одной случайной подвыборки.

- `--runs` прогонов (по умолчанию 10), `--sample` переводов на прогон (80).
- Выборка (`sample_significant_translations`): случайные статьи, у которых есть
  перевод; между прогонами копится `used` — статьи не повторяются, каждый
  прогон видит свежую лексику.
- Из выборки **исключаются служебные части речи** (союз, частица, предлог,
  послелог, междометие — `SERVICE_POS_KEYWORDS`, матч по подстроке в `Tag.name`):
  у них нет предметного смысла.
- Промпт проектирования (`ONTOLOGY_SYSTEM`) требует:
  - **25-30 ШИРОКИХ полей**, жёсткий потолок 30 (перебор → объединять);
  - запрет узких микрополей (не «раскалывание», а «Физические действия»);
  - запрет функционально-грамматических полей (интенсивность, модальность,
    причинность, сравнение) — это грамматика, не смысл;
  - обязательное покрытие И специальной лексики (растения, животные,
    ткачество, земледелие, жилище), И общеупотребительной (действия, движение,
    тело, эмоции, речь, восприятие, пространство, время).

Выход: `{"designs": [...N наборов...], "meta": {...}}`.

Фактический прогон перед заморозкой — 10 прогонов по 80 переводов:

```
docker exec --user 1000:1000 -w /app/agents punzh_django \
  python build_ontology.py --design-only --runs 10 --sample 80 --out designs10.json
```

### 3.2. Усушка (`--consolidate`)

Свести N черновиков в один согласованный список (`consolidate_ontologies`,
`CONSOLIDATE_SYSTEM`):
- объединить синонимы и расщеплённые близкие поля («Речь и звуки» = «Звуки и
  речь» = «Речь и коммуникация» → одно);
- **жёстко выкинуть** функционально-грамматические и оценочно-модальные поля,
  даже если они всплыли во многих прогонах;
- редкие узкие поля из одного прогона растворить в широкие;
- итог — **20-28 полей**, каждому единое чистое определение.

Выход: `{"ontology": [{"field","definition"}]}`. Его **оценивают глазами** и
**замораживают** — это `dict/fixtures/custom/ontology_frozen.json`.

### 3.3. Загрузка онтологии в справочник (`load_semantic_fields`)

Заморозку заливаем в `SemanticField` **до** разметки:
- по умолчанию **мягко** (`update_or_create`): обновить определения, добавить
  новые, ничего не удалять; `sorting` = порядок поля в онтологии;
- `--force` — снести весь справочник и пересоздать; **каскадом** уносит все
  привязки `ArticleSemanticField`. Опасно, за `--yes`-подтверждением;
- формат — наш `{"ontology":[...]}`, НЕ Django-fixture.

### 3.4. Прогон для разметки (`--ontology FROZEN --limit N`)

Классификация всех статей по замороженной онтологии:
- промпт `SYSTEM_PROMPT_FROZEN` (общий модуль `dict.ai.prompts`): относить
  **строго** к полям из списка, новые заводить **запрещено**, 1-3 самых
  релевантных поля; служебное слово → пустой список и `no_field: true`;
- в коде страховка: левые поля отсекаются (`f in field_defs`);
- вход по статье — переводы + русские фрагменты иллюстраций;
- устойчивость долгого/платного прогона: **автодокат** (если выходной файл уже
  есть — обработанные id пропускаются, продолжаем с остатка), `_flush()` каждые
  100 статей, `temperature=0`.

Выход: `{"assignments" {id:[поля]}, "keywords" {id:[...]}, "no_field_ids",
"errors", "field_definitions", ...}`.

## 4. Загрузка разметки в БД

**`load_semantic_classification --file`** — `assignments` → `ArticleSemanticField`:
- JSON — **источник истины, но точечно**: для статей из json старые привязки
  удаляются и создаются заново; статьи вне json не трогаются (можно
  переразметить часть словаря, не задев остальное);
- поля ищутся по имени (`name→id` одним запросом); несуществующие статьи и
  отсутствующие в справочнике поля не валят импорт, а репортятся в конце;
- `bulk_create(ignore_conflicts=True)` пачками — быстро и идемпотентно.

**`load_keywords --file`** — `keywords` → `ArticleKeyword` (сырьё как есть,
чистка от шума запланирована **программной**, не LLM). Отдельный слой для
обогащения русского поиска: транзитивный путь keyword→статья→поля.

Стык с AI-поиском и с `/ontology/`:
- группа «по смысловому полю» и список статей поля = чтение
  `ArticleSemanticField`;
- статьи с `no_field` (отсылки «см. X» без своего смысла) **не** заливаются в
  поля — подтягиваются на лету через входящий `ArticleLink` (на сайте:
  `article_ids_for_semantic_field` в `dict/search.py`). Поле в БД не копируется.

Просмотр (закрытая бета, без ссылки в шапке): `/ontology/`, `/ontology/<id>/`.
Справочник и привязки в админке только читаются; правка — перезаливкой JSON.
Выдача `/ontology/` **не** фильтрует по `from_translation`: статья во всех своих полях.

### 4.1. Поле из перевода (`from_translation`)

Отдельный проход, не переклассификация и не «одно главное». Классификатор
смотрел ещё и иллюстрации, поэтому у части статей соседний смысл примера
попал в список полей. `pick_translation_fields.py` помечает, какие из уже
стоящих полей следуют из **переводов леммы**: в промпте только переводы
и закрытый список полей. Несколько True — многозначность; пустой список —
ни одно поле не про лемму. Одно поле тоже спрашиваем у модели.
Заливка `load_translation_fields` трогает только флаг.
Боевой прогон DeepSeek — `backlog.md` §4 (очистка переводов на prod
закрыта — `docs/translation_cleanup.md`).

**Результат (dev и прод совпадают):** 28 полей, 28262 привязки (~1.77 на
статью), 48065 keywords, `no_field` ~7% (здоровый уровень). Мёртвых полей нет —
коридор 25-30 → усушка до 28 сработал, поля широкие и реально наполняются.

### Порядок боевого прогона

1. `build_ontology.py --design-only --runs 10 --sample 80 --out designs10.json`
   → 10 сырых онтологий (фактический прогон перед заморозкой);
2. `build_ontology.py --consolidate <designs>` → усушка в один список;
3. оценить глазами, заморозить → `ontology_frozen.json`;
4. `load_semantic_fields` → залить справочник;
5. `build_ontology.py --ontology ontology_frozen.json --limit ...` → прогон по
   всем статьям (автодокат до полного покрытия);
6. `load_semantic_classification --file <classified_all.json>` → залить привязки;
7. `load_keywords --file ...` → залить keywords.

Шаги 1-3, 5 — оффлайн в `app/agents/` через DeepSeek; шаги 4, 6, 7 —
management-команды Django.

Отдельно от прогона онтологии выше: `pick_translation_fields.py` →
`load_translation_fields` (`backlog.md` §4). Поля уже стоят, меняется только
флаг `from_translation`.

## 5. Доклассификация нового слова

После массового прогона словарь живёт: в админке появляются новые статьи.
Их нужно разметить тем же правилом, без повторного прогона всех 16k.

**Команда:** `manage.py classify_article --id <article_id>`  
**Ядро:** `dict.ai.classify.classify_article` (без HTTP — можно звать из фона).  
**Канал:** Timeweb → DeepSeek (`TIMEWEB_AI_MODEL_CLASSIFY`). Проверка шлюза:
`manage.py test_timeweb`.

Поведение:
- онтология — из `SemanticField` (не из файла);
- промпт и вход статьи — те же, что у пакетного `--ontology`;
- пишет **только** эту статью: старые `ArticleSemanticField` /
  `ArticleKeyword` заменяются; остальные статьи не трогает;
- левые имена полей отсекаются; keywords — с той же санитарией, что
  `load_keywords` (strip/lower, длина ≥ 2, не чисто цифры);
- `no_field` / пустой список → привязок нет, keywords всё равно пишутся;
- `from_translation` — второй LLM-вызов в том же `classify_article`: какие из
  проставленных полей следуют из `ArticleIndexTranslate` (без HTML; смыслы
  аддендумов уже в индексе); при сбое второго вызова поля пишутся с
  `from_translation=False`;
- `--dry-run` — только ответ модели, без записи;
- сбой LLM / пустой справочник / нет статьи → `ok=False`, БД не меняется.

Фон (позже): вызывать ядро после сохранения статьи (не из `Article.save()` —
инлайны переводов пишутся позже); в воркере — `close_old_connections()`
вокруг вызова, не внутри ядра.

```bash
# дым
docker exec --user 1000:1000 -w /app punzh_django \
  python manage.py classify_article --id 12345 --dry-run

# запись в БД
docker exec --user 1000:1000 -w /app punzh_django \
  python manage.py classify_article --id 12345
```
