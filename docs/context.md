## **1. Назначение проекта**

Проект представляет собой веб‑версию фундаментального словаря карельского языка (тверские говоры), созданного Пунжиной А. В. и опубликованного в 1994 году в Петрозаводске (Карелия) при участии Карельского научного центра РАН.  
Словарь содержит уникальные этнографические, диалектологические и лингвистические материалы, собранные автором за многие годы полевых исследований. Тверской диалект карельского языка является одним из малых языков России, и словарь представляет собой важный научный и культурный источник.

Веб‑версия проекта включает:

- все слова оригинального печатного издания 1994 года;
- поздние исправления и дополнения автора, отсутствующие в бумажной версии;
- расширенные возможности поиска, включая поиск по расстоянию Левенштейна и варианты написания слов;
- удобную навигацию по статьям, тегам и источникам;
- статические страницы, посвящённые диалекту, языку и истории проекта.

Цель проекта — сохранить, систематизировать и предоставить широкий доступ к уникальному лингвистическому наследию тверских карел, обеспечив современный интерфейс для исследователей, филологов, студентов и всех интересующихся карельским языком.

Проект реализован как классический **монолитный Django‑приложение** с MVC‑структурой:

- Models — доменные сущности  
- Views — контроллеры

## **6. Потоки данных и взаимодействие компонентов**

1. Пользователь отправляет запрос на поиск.  
2. `views.py` вызывает `search.py`.  
3. `search.py`:
   - нормализует слово;  
   - генерирует варианты написания;  
   - выполняет поиск по Article;  
   - использует Levenshtein при неточных совпадениях.  
4. Результаты передаются в шаблон.  
5. Шаблон рендерится в HTML.  
6. Django Admin управляет статьями, тегами и источниками.  
7. Импорт данных загружает JSON‑файлы в ORM.

---

## **7. Ограничения и допущения**

- Монолитная архитектура.  
- Нет REST API — взаимодействие через HTML.  
- Нет асинхронных задач (Celery, Redis).  
- Поиск реализован на Python без внешних движков.  
- Производительность зависит от оптимизации ORM и алгоритмов.  
- Большой объём статических файлов (частично стандартный Django Admin).

---

## **8. Принятые архитектурные решения**

- Django выбран как основной фреймворк.  
- Монолит оптимален для словарного проекта.  
- ORM используется для хранения словарных данных.  
- Поиск реализован через Python‑алгоритмы для гибкости.  
- Использование расстояния Левенштейна для неточных совпадений.  
- Helpers вынесены для чистоты кода.

---

## **9. Технические риски**

- Рост объёма словаря может замедлить поиск.  
- Отсутствие индексации усложняет оптимизацию.  
- Монолит затрудняет масштабирование.  
- Нет API для интеграции с внешними сервисами.  
- Импорт больших объёмов данных может быть медленным.
