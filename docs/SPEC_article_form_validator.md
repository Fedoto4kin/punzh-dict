# SPEC — валидатор согласованности статьи + черновик нового слова

Проект: punzh-dict. Форма редактирования слова (админка/редактор).
Область: НЕ генератор (html остаётся источником истины). Помогает автору:
(1) собрать ЧЕРНОВИК для нового слова из полей формы; (2) СВЕРЯТЬ согласованность
html ↔ структура для существующих и предупреждать о расхождениях.

Отменяет тяжёлые вопросы общего backlog-gen-article (модель A/B, миграция 16k):
существующий html НЕ перезаписываем, только проверяем. Черновик — только для
новых, одноразово (строительные леса).

---

## Опознание помет в тексте (как в reindex_tags)

Помета считается «упомянутой в html», если найдена её игла:
- типы 1-4: `<i>{tag.value}</i>`
- тип 5: голый текст `{tag.value}`
Тот же матчинг, что в `reindex_tags` — консистентность обязательна (иначе ложные
предупреждения). Справочник — `Tag` (value, type).

Переводы: сверять `ArticleIndexTranslate.rus_word` статьи с наличием в тексте.
Связи «см.»: сверять `ArticleLink` (to_article) с «см. {слово}» в тексте.

## Часть 1 — ЧЕРНОВИК нового слова (js, клиент)

Условие: html ПУСТ (новое слово).
Источник: ПОЛЯ ФОРМЫ (заполненные автором: слово, пометы-селекты, переводы,
см-связь).

js собирает по шаблону:
    {слово} {пометы} {переводы через запятую} {см. связь}

Пометы — в фиксированном ПОРЯДКЕ по типу:
    часть речи · уточнение части речи · диалект · нас. пункт · семантический окрас
(js знает тип каждой выбранной пометы из Tag.type, расставляет по порядку.)
Пометы оборачиваются `<i>...</i>` (кроме типа 5 — голым текстом).

Пример результата:
    kaz’in|poiga <i>s</i> котёнок; ...
    (слово + <i>s</i> сущ. + перевод «котёнок»)

Черновик кладётся в поле html. Дальше автор ПРАВИТ руками (примеры употребления,
типографику). Одноразово — после правки html главный, поля не перегенерируют.

ЕСЛИ в html уже есть эти данные — ничего не менять (не дублировать).

## Часть 2 — проверки согласованности (существующее слово, есть html)

При сохранении. Обе стороны:

### A. Текст → структура (в тексте есть, в полях нет)
Для каждой пометы/перевода/см, УПОМЯНУТОЙ в html (по игле), проверить, есть ли
соответствующая запись в структуре (ArticleIndexTag / ArticleIndexTranslate /
ArticleLink). Если в тексте есть, а в структуре нет → РАСХОЖДЕНИЕ A.
Смысл: «текст говорит о помете „всг.", но в полях статьи её нет».

### B. Структура → текст (в полях есть, в тексте нет)
Для каждой пометы/перевода/см В СТРУКТУРЕ проверить, упомянута ли в html.
Если в структуре есть, а в тексте нет → РАСХОЖДЕНИЕ B.
Смысл: «у статьи помета „бранное" в полях, но в тексте не упомянута».

### Реакции (ЕДИНООБРАЗНО для A и B)
И расхождение A, и расхождение B → при сохранении показать ПРЕДУПРЕЖДЕНИЕ и окно
ПОДТВЕРЖДЕНИЯ / ОТМЕНЫ сохранения. Не мягкое «просто сообщили» — сохранение
проходит только после подтверждения автором, иначе отменяется. Автор сам решает,
что верно (текст или поля), правит и сохраняет заново.

ВАЖНО: в html НИЧЕГО не добавляем автоматически (ни при A, ни при B). Только
сообщаем и ждём подтверждения/отмены.

## Открытые вопросы
1. Реакции: какая сторона (A или B) — мягкое предупреждение, какая —
   подтверждение/отмена? (по тексту автора: обе есть, распределить).
2. Иллюстративные примеры (`~ pagizow`) — в структуре не представлены; черновик
   их не соберёт, автор дописывает руками. Ок для MVP.
3. Парсинг помет по `<i>value</i>` — рукописный текст может отклоняться
   (пробелы, регистр). Начать с точного совпадения (как reindex_tags), при шуме
   — уточнить.
4. Где живёт валидатор: Django-форма (clean/save) для серверных проверок части
   2; js для черновика части 1. Часть 2 может быть и на сервере (надёжнее), и
   на клиенте (быстрее). Решить.

## Что переиспользуем
- `reindex_tags` — логику игл `<i>value</i>` / тип 5 (матчинг помет в html).
- `Tag` (value, type) — справочник и порядок помет.
- `ArticleIndexTranslate`, `ArticleLink` — структурные переводы и связи.

## Сопутствующие валидаторы формы (побочно, связаны)

### В1 — уникальность помет и связей в форме
Проблема: инлайны позволяют вбить ДУБЛЬ (одна помета/связь дважды).
Уровни:
- БД уже защищена: `ArticleIndexTag` unique_together (article, tag);
  `ArticleLink` unique_together (from_article, to_article). Дубль → IntegrityError
  (грубо, невнятно в админке).
- Нужен дружелюбный уровень ФОРМЫ: `formset.clean()` ловит повтор среди инлайнов
  ДО сохранения и даёт понятную ошибку («эта помета уже добавлена»), а не 500.
Реализация: clean() на инлайн-формсетах помет и связей — собрать значения,
проверить на дубли, ValidationError при повторе.

### В2 — виджет поиска для связанной статьи «см.»
Проблема: селект `to_article` показывает ВСЕ ~16k слов алфавитно — невозможно
пользоваться.
Решение: `autocomplete_fields = ("to_article",)` в инлайне ArticleLink — поле с
ПОИСКОМ (печатаешь → фильтр), как уже сделано для `tag` в ArticleIndexTagInline.
Требует `search_fields` у ArticleAdm (есть: `("word",)`). Поиск пойдёт по
карельскому слову; при желании добавить `word_normalized` в search_fields Article
для поиска и по нормализованной орфографии.
Тот же отлаженный механизм автокомплита, что для помет — переиспользуем.
