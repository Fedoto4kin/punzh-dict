# Спецификация v3: подсказки поиска — реализовано + бэклог

Статус: **лексический baseline готов (2026-08-30).** Область: русская ветка
`search()` → `search_by_translate_linked`. Дата первой реализации: 2026-08-01.

---

## 0. Что стоит в коде (одной фразой)

По **русскому** запросу (`detect_direction` → `search_by_translate_linked`):

1. **Полная выдача** — ILIKE по `rus_word` (= запрос, целая строка) + **токенный
   OR** (каждый токен запроса — целое слово в переводе; fuzzy одна буква для
   длины ≥5: корова/корове), объединение, затем расширение через
   `expand_by_links` (**см.+от**, `KINDS_LISTING`; **ср.** не расширяет).
2. Под выдачей — **сужающие теги** (`?f=<ключ>`, AND по токенам key; скобки в
   label, не в key) и **точные соответствия** (`?f=exact`) — оба через `?f`.
   Блок «Уточнить запрос» **только если есть теги**; иначе блок не показывается.
3. **Связанные запросы** — однословные синонимы статей с ILIKE-попаданием.

Запрос перед поиском: **ё→е** во `views.search`.

Похожих/переходов внутри выдачи по тегам нет как класса — доказано (Приложение A).

## 0.1 Ожидаемое поведение (русский поиск)

### Полная выдача (без `?f`)

| Источник попадания | Пример |
|---|---|
| ILIKE: `rus_word` **равен** запросу | «быстро» → `ruttoh` (перевод «быстро») |
| Токен: слово запроса **целиком** в переводе | «быстро» → `ehatta` («быстро **ехать**») |
| Связь ArticleLink (**см.+от**) с любой статьёй выше | «быстро» → соседи по см./от из кластера |

Статья с переводом «медленно», связанная с `ruttoh`, **может** быть в полной
выдаче (если попала через link-expand), но **не** в «точных».

### «Точные соответствия» (`?f=exact`)

Показываются статьи, у которых:

- есть запись `rus_word`, **точно равная** запросу (после ё→е); **или**
- **нет** своих переводов в индексе, но есть связь (1 хоп, см.+от) со статьёй
  из первой группы (`rutoldi` → «см. ruttoh»).

**Не показываются:** статьи только из link-expand / токенного match, у которых есть свои
переводы, но **нет** строки `rus_word` = запрос.

Кнопка «Точные соответствия» — **внутри блока «Уточнить запрос»**, только если есть
сужающие теги (`has_direct` и непустой `narrowing`).

### Сужающие теги (`?f=<ключ>`)

Кандидаты из token-match; **label** = полная фраза перевода; **key** = фраза без
скобочных помет `(…)`, слов запроса и стоп-слов. Фильтр `?f=` — **AND** по всем
токенам key. Coverage — AND по key в блобе карточки.

Пример: запрос «быстро» → тег с ключом `ехать` → только `ehatta`.

### Эталон «корова» / `enži|kandon'e` (после очистки переводов)

Статья id **1717**: узкое значение «первотельная (о корове)», в индексе **нет**
голого «корова».

| Запрос | Полная выдача | Точные | Уточняющий тег |
|---|---|---|---|
| первотельная | да (токен) | нет¹ | — |
| первотельная корова | да | да (ILIKE) | — |
| корова | да (токен + fuzzy корове) | **нет** | тег `?f=первотельная` |

¹ Если нет отдельной строки `rus_word` = «первотельная».

DB-тест: `test_search_korova.py`.

**После очистки переводов**

Ожидание: меньше мусорных однословных осколков → чище полнотекст и теги;
«точные» станут ближе к «слово = перевод-лемма», без лишних статей с
разорванными фразами в индексе. Семантика `?f=exact` **не меняется** — только
качество данных.

## 1. Реализовано: сужающие теги — `split_by_coverage`

`split_by_coverage(candidates, page_blobs, query_words, stopwords) -> narrowing`

- **Ярлык** (показываем) = токены кандидата минус слова запроса (`query_words`,
  ТОЧНОЕ совпадение), стоп-слова сохранены.
- **Ключ** (фильтруем) = ярлык минус стоп-слова.
- **Покрытие** = число карточек выдачи, чей блоб переводов содержит хотя бы
  один токен ключа (подстрокой).
- Класс: `0 < покрытие < N` → тег; `покрытие ∈ {0, N}` или пустой ключ →
  отброшено.
- Возврат: `[{"label","key","coverage"}]`, дедуп по ключу (первый ярлык),
  сортировка по возрастанию покрытия.

Токенизация: `_TOKEN_RE = [а-яё\-]+` (совпадает со стоп-листом; `что-л.` →
`что-л`). Стоп-лист `STOPWORDS = _STOP_1A | _STOP_1B` — модульная константа в
`search.py` (корзины 1a: `len<=2`; 1b: пометы на `-л`).

Тесты: `test_split_by_coverage.py`, 9 шт., `SimpleTestCase`.

## 2. Реализовано: точные соответствия — `find_exact_match_ids`

`find_exact_match_ids(result_ids, ilike_ids, blobs_by_article, links) -> set(article_id)`

Статья попадает в «точные соответствия» двумя путями:
- **прямое**: хотя бы одна запись `rus_word` совпадает с запросом (ILIKE после
  нормализации ё→е во `views.search`; для однословного запроса это ровно
  «быстро» = «быстро», не «быстро ехать»);
- **наследованное**: у статьи НЕТ своих переводов, но она связана
  (`ArticleLink`, любое направление, **один хоп** внутри выдачи) хотя бы с
  одной статьёй с прямым ILIKE-попаданием (`rutoldi` → «см. ruttoh»).

**Не включаются** статьи, попавшие в выдачу только через `expand_by_links` или
полнотекст, если у них **есть свои переводы**, но **нет** точного совпадения
`rus_word` с запросом (напр. `linkedown` с «медленно» при запросе «быстро»).
Статья с ILIKE-попаданием остаётся точной даже при наличии других фразовых
переводов (`maihahtua`: «быстро» + «быстро пробежать»).

Тесты: `test_find_exact_match_ids.py`, `SimpleTestCase`.

## 3. Реализовано: встраивание и фильтр — `search_by_translate_linked`

Сигнатура: `search_by_translate_linked(query, page=1, f=None)` →
`(page_obj, found_count, narrowing, direct_ids)`.

Порядок: считаем полную выдачу (`result_ids`), `blobs_by_article` (переводы по
статье, ОДНИМ запросом), `candidates`, `narrowing`, связи внутри выдачи (обе
стороны), `direct_ids`. Затем фильтр — **после** тегов/прямых (они всегда от
полного якоря) и **до** пагинации (иначе поедут номера страниц и n-граммы):

- `f == "exact"` → `result_ids & direct_ids` (direct_ids = find_exact_match_ids);
- `f == <ключ>` → карточки, чей блоб содержит ЛЮБОЙ токен ключа (та же логика,
  что считала покрытие → число совпадает с тем, что на теге);
- иначе → полная выдача.

## 4. Реализовано: вью и UI

`views.search`: читает `?f`, распаковывает 4 значения, считает `active_label`
(подпись активного фильтра: `«точные соответствия»` или `label` тега по `key`),
кладёт в контекст `narrowing`, `has_direct`, `active_f`, `active_label`.

`search.html`:
- блок «Уточнить запрос» **свёрнут по умолчанию** (`collapse` без `show`);
- активный фильтр — **кликабельный badge** в заголовке; клик по badge ведёт на
  `/search/<query>/1` без `?f` (снять фильтр, сброс на стр. 1);
- чипы-теги (`?f=<ключ>/1`), активный подсвечен `btn-primary`;
- кнопка **«Точные соответствия (без уточнений)»** (`?f=exact`), `btn-info`;
- тоггл «свернуть/развернуть» — 3 CSS-правила на `.collapse-toggle` +
  штатный класс `.collapsed` от Bootstrap.

URL-схема: `/search/<query>/<page>?f=<ключ|exact>`. `?f` — GET-параметр, читается
во вью; `urls.py` не менялся.

## 5. Принятые ограничения (осознанные, не баги)

- **Морфоварианты запроса просачиваются в ярлык.** `query_words` вычитается
  точным совпадением, поэтому `быстрый`/`быстрее` при запросе `быстро` не
  вычитаются. Чинится стеммером (бэклог). Зафиксировано тестом
  `test_query_form_variant_leaks_into_label`.
- **Покрытие по подстроке** (`лес` матчит `лесной`) — взято для согласованности
  с диагностикой; при шуме заменить на токен-точное.
- **Многословные ключи плодят почти-дубли** (`ехать` и `ехать лошади`) — дедуп
  по точному ключу их не схлопывает.
- **Наследование прямоты — один хоп**, связи только внутри выдачи.
- **DB-тесты фильтра:** `test_search_filter.py` (5 шт.) — полный путь
  `search_by_translate_linked` с `?f=exact` и `?f=<ключ>`.

## 6. Бэклог с заметками по реализации

### 6.1 Тесты на живой фильтр
**Сделано:** `test_search_filter.py` — exact, key, наследование rutoldi,
исключение linked-with-own-translations. При изменении семантики — дополнять.

### 6.2 «Связанные запросы» через синонимию
**Сделано:** `find_related_queries` в `search.py`, блок в `search.html`,
тесты `test_find_related_queries.py`. Односложные синонимы ILIKE-попаданий —
выходы наружу выдачи (`ruttoh` → `круто`, `скоро`); клик = новый поиск.
Не путать с `find_exact_match_ids`.

### 6.3 Механизм 2 — спасение запроса (fuzzy) на пустой выдаче
Когда `found_count == 0`: `TrigramSimilarity("rus_word", query) > 0.3` →
близкие по написанию переводы. Проверено (Приложение B): `говрить→говорить`,
`кошку→кошка`. НЕ переиспользовать `search_possible` — он ищет по
`ArticleIndexWordNormalization` (карельский латинский индекс), на кириллицу даёт
`[]`. Отдельная ветка по `rus_word`. Не ловит словоизменение (`идёт→идти`).

### 6.4 Стеммер морфоформ (pymorphy или суррогат-префикс)
Вычитание по основе вместо точного. Чинит СРАЗУ две вещи: убирает
`быстрый/быстрее` из тегов (мусор) И собирает их в точные соответствия. На данных
префикс `быстр` добавлял к точным 4 формы, `быст`/`быстр` без ложных
срабатываний. pymorphy — тяжёлая зависимость; суррогат `startswith(query[:5])`
дёшев, длину мерить на данных.

### 6.5 Семантические соседи — pgvector (глубокий слой)
LaBSE/XLM-R + pgvector, отдельный блок «Нашли по смыслу». Четвёртый, самый
глубокий механизм. Контекст вью уже отдаёт именованные ключи — новый блок
встанет рядом, шаблон переписывать не нужно.

### 6.6 Прочее
- Схлопывание вложенных ключей (`ехать` ⊃ `ехать лошади`) против почти-дублей.
- Покрытие: подстрока → токен-точное, если всплывёт шум.
- Косметика: цвет кнопки «Точные» (жёлтый плохо читался на белом → `btn-info`).
- «Слишком общие» ключи (`делать` 16/81) — пока в хвосте сортировки, потолок не
  вводим (нет данных обосновать порог).

## Приложение A. «Переходов в лексике нет» (доказано)

Кандидаты берутся из фултекста по якорю; `article_id` каждого ∈ выдачи → перевод
кандидата в блобе его карточки → покрытие ≥ 1 → `coverage == 0` недостижимо.
Свойство источника, не данных. Эмпирика: 200 случайных запросов → «непустой
similar» = 0; «пустая выдача» = 100/200 (материал для механизма 2). Прямые
попадания и «связанные» обходят это, т.к. приходят из графа связей/синонимии, а
не из фултекста.

## Приложение B. Эталон «быстро» (актуальная семантика exact)

Синтетические тесты (`test_search_filter.py`): 5 статей, запрос «быстро».

| Статья | В полной выдаче | В `?f=exact` | Почему |
|---|---|---|---|
| ruttoh | да | да | ILIKE «быстро» |
| maihahtua | да | да | ILIKE «быстро» (есть и фраза) |
| ehatta | да | нет | только FTS «быстро ехать» |
| rutoldi | да | да | нет переводов, link → ruttoh |
| linkedown | да | нет | свои переводы, нет ILIKE |

На боевых данных (запрос «быстро», до очистки переводов, ориентир 2026-08):

- Полная выдача: ~72 статьи (ILIKE + FTS + link-expand).
- Точные (`find_exact_match_ids`): статьи с `rus_word` = «быстро» плюс
  translationless по связи; синонимы ruttoh («круто», «скоро») — **отдельные**
  запросы, не попадают в exact для «быстро».
- Fuzzy по `rus_word` (бэклог): `говрить→говорить`, `кошку→кошка`;
  `идёт→идти` не находится.

## Приложение C. Уроки инфраструктуры

- **Диагностические скрипты под `manage.py shell < file`: только плоский код.**
  Ни функций верхнего уровня, ни comprehensions (list/dict/set/generator) — оба
  создают свой скоуп и не видят имён скрипта под `exec()`. Только модульные циклы
  с `.append()`.
- **Тесты запускать с `-w /app`.** Пустой `__init__.py` в `/app` превращал корень
  в пакет `app`, модули резолвились как `app.dict.*` → ошибки `app_label`. Файл
  удалён; запуск из `/app`.
