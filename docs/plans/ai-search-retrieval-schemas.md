# AI-поиск: декларативные схемы retrieval

**Статус:** бэклог (отдельная задача, не смешивать с текущими правками parse/search).  
**Связано:** `app/dict/ai/search.py`, `docs/ai-search.md`, `docs/SPEC_ai_query_parse.md`.

## Зачем

Правила «говор + тема», soft/hard-пометы, POS-сужение, demote см./без перевода
сейчас размазаны по веткам в `search_by_parsed`. На запросах вроде
«весьегонские слова про погоду» легко уйти в круг эвристик; поведение
предсказуемо на данных, но **непрозрачно** для продукта и тестов.

Нужны явные схемы (YAML и/или Python-структуры): код только исполняет схему
(какие оси → какие множества → union/intersect → demote/ранг), без новой
импровизации в if/else.

## Черновик контракта (не код)

Вход: валидированный parse (`lexical`, `related`, `fields`, `tags`,
`tags_soft`, `dialect`, …).

Слои (пример):

1. `anchors` — переводы `lexical|focus|related` ∩ поля (без KW-иллюстраций)
2. `anchors ∩ dialect` — приоритет, если говор задан
3. `field ∩ dialect` — browse темы в говоре (не весь словарь)
4. demote: см./от pull-ins; статьи без `ArticleIndexTranslate`
5. не подменять говор не-диалектными глоссами (`dialect_relaxed` только если
   `field ∩ dialect = ∅`)

Ограничение данных (зафиксировать в схеме/доке): поле «Природа и погода»
шире погоды; пересечение погодных переводов ∩ всг. почти пусто → топ
тема∩всг. будет ландшафт/смежное — это не баг retrieval.
