# Методика AI-поиска: retrieval и схемы

Как устроен и **как эволюционировал** retrieval `/ai-search/` (после parse).
Дополняет UX (`ai-search.md`) и контракт разбора (`SPEC_ai_query_parse.md`)
со стороны правил выдачи. План схем: `plans/ai-search-retrieval-schemas.md`.

---

## 0. Урок: фейлы — часть методики, не мусор

При разметке онтологии (`method-onthlogy-markup.md`) после успеха почти не
осталось зафиксированных **провалов и отвергнутых гипотез** — для статьи и
для повторной калибровки это дыра: видно «как стало», не видно «что ломалось
и почему отвергли».

**Правило для этого контура:** любой отказ гипотезы, регресс, «кажется баг,
а это данные», ложный топ — пишется сюда **в день решения**, до того как
код/промпт это сотрут. Тесты хранят исполняемый эталон; этот файл — **нарратив
и контекст для статьи / отчёта** (почему так, что пробовали, чего не хватает
в разметке).

Не путать три полки:

| Полка | Пример | Куда |
|-------|--------|------|
| **Баг retrieval** | говор подменён не-всг. глоссами | фикс + тест + запись «было→стало» |
| **Отказ гипотезы** | LLM re-rank не поднял точный перевод | вердикт + условия прогона; код удалён |
| **Предел данных** | погода∩всг. почти пусто → ландшафт в том же поле | не «чинить» поиском; писать как ограничение разметки |

---

## 1. Цель retrieval

После валидированного parse собрать **прозрачную** выдачу: пользователь видит
оси («как поняли»), а статьи ранжируются детерминированно (focus ≫ lexical ≫
поле; demote см./без перевода). Не чёрный ящик второго LLM без доказанной
пользы.

Контур **не** смешивать с лексическим `/search/` и с оффлайн `agents/`.

---

## 2. Слои (зафиксированный pipeline)

```text
query → parse (1.15) → resolve sets → profile (схемы) → POS → soft
      → expand см./от + demote → rank → UI groups
```

- Parse: `query_parse.py` / SPEC.
- Sets + профили: `retrieval_schemas.py` (`PROFILES`); `search_by_parsed` —
  resolve → match → apply → POS/soft/demote.
- Rank: `rank.py` (вне схемы профилей).
- LLM re-rank: удалён; см. §4 и `plans/ai-search-llm-rerank.md`.

Формат схем (согласовано 2026-10-24, в коде 2026-11): Python dataclasses,
union-кортежи имён множеств, POS/soft после профиля, 6 профилей v1 — детали
в плане.

## 3. Корпус кейсов

Исполняемые проверки: `dict.tests.test_ai_search` (+ живой
`manage.py ai_query` на prod/dev). Ниже — **подпись для методики**; при
расхождении с тестом править оба.

### 3.1. Эталоны поведения (успех после фикса)

| Запрос / ситуация | Ожидание | Тест / проверка |
|-------------------|----------|-----------------|
| «весьегонские слова про погоду» | ~68 всг., без `dialect_relaxed`; tier1 anchors∩всг., tier2 поле∩всг. | `test_dialect_label_theme_*`; живой prod |
| anchors | tr(lexical\|related\|focus) ∩ поле, **не** KW | docstring / label_theme |
| KW «дождь» на муравейнике / чибисе | demote / не топ | `zero_kw` в label_theme; illustration tests |
| см. входящие / без `ArticleIndexTranslate` | demote относительно прямых | `test_see_referrer_demoted_*`, `test_no_translation_demoted_*` |
| «весьегонский говор» (без темы) | обзор всг. | `test_dialect_only_*` |
| POS + тема | POS сужает, не `main = field∩v` | `test_pos_narrows_theme_*` |
| soft-помета | union soft∩field, не опустошение | `test_soft_tag_*` |

### 3.2. Ограничения данных (не баг поиска)

| Наблюдение | Почему не чиним retrieval | Для статьи |
|------------|---------------------------|------------|
| «погода»∩всг. по переводам почти пусто; топ = ландшафт/смежное из «Природа и погода»∩всг. | поле шире узкой погоды; всг. погодная лексика слабо представлена в tr∩поле | оговорка: выдача ограничена разметкой и шириной поля |
| Theme browse под говором ≠ «все слова про X в языке» | фильтр говор∧поле | честная подпись осей важнее полноты |

#### 2026-10-24 — LLM re-rank топ-30

- **Гипотеза:** второй проход LLM улучшит порядок SQL (точный перевод выше
  ложных друзей) и обрежет хвост (`keep_tail`).
- **Проверка:** `manage.py compare_ai_models`, 22 эталона; несколько моделей
  шлюза; одна SQL-голова.
- **Результат:** ни разу не подняли статью с точным переводом выше SQL;
  редкие сдвиги вниз; частый `keep_tail=false` режет тематический обход;
  таймауты у части моделей.
- **Решение:** отвергнуто; код и env-ключи сняты (2026-11).
- **Для статьи:** детерминированный rank по осям оказался устойчивее
  «мягкого» LLM-переранжирования на этом словаре и наборе запросов.

#### 2026-11-11 — декларативные профили retrieval

- **Гипотеза:** вынести ветки `search_by_parsed` в таблицу `RetrievalProfile`
  (6 профилей); интерпретатор только исполняет.
- **Проверка:** `manage.py test dict.tests.test_ai_search`.
- **Результат:** поведение эталонов сохранено (рефактор без смены семантики).
- **Решение:** принято.
- **Для статьи:** правила выдачи можно цитировать как таблицу профилей.

#### 2026-10 — подмена говора / dialect_relaxed слишком рано

- **Гипотеза (ошибочная ветка):** при слабом lexical∩всг. показать тему по
  всему словарю или ослабить говор, чтобы «не пусто».
- **Симптом:** не-всг. глоссы выглядят как ответ на «весьегонские…»; или
  дамп всех всг. вместо темы.
- **Решение:** профиль label_theme: main = tier1∪tier2; relax только если
  `field∩dialect = ∅`; не подменять говор чужими глоссами.
- **Для статьи:** конфликт полноты и честности фильтра; выбран честный говор
  ценой более «ландшафтного» топа при дырявом ∩ лемм.

#### 2026-10 — KW-иллюстрации в топе темы

- **Гипотеза (ошибка ранга):** keyword «дождь» усиливает релевантность статьи
  муравейника/чибиса в теме погоды.
- **Решение:** в label_theme обнулить KW-score; demote статьи без своего
  перевода.
- **Для статьи:** иллюстративный слой онтологии (keywords) опасен как сигнал
  retrieval без отдельного веса/контура.

#### 2026-10 — имена полей в parse без definition

- **Гипотеза:** упростить вход модели, убрать definition полей.
- **Результат:** откат (качество осей хуже / нестабильнее — зафиксировать
  детали при наличии лога; иначе пометить «нужен добор улик»).
- **Решение:** отвергнуто; промпт 1.15 с definitions.
- **Для статьи:** краткость входа модели ≠ качество разбора на закрытом
  справочнике полей.

## 4. Как вести дальше (чеклист при каждой правке retrieval)

1. Воспроизвести запрос или тест **до** фикса (что именно плохо).
2. Добавить/обновить тест, если поведение должно заморозиться.
3. Запись в §3.3 или §3.2 **в том же PR/чате**, что и код.
4. Не удалять записи отказов при чистке кода — только помечать
   «код удалён YYYY-MM-DD».
5. `research/` не засорять черновиками продукта; в статью переносят
   обобщение из этого файла, не сырой git-diff.
