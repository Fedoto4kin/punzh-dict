## ГРАНИЦА: это ЛЕКСИЧЕСКИЙ поиск, НЕ семантика

Документ — про «классический» поиск: точное/подстрочное совпадение, синонимия
по соседству в статье, морфоформы (леммы). Семантику и эмбеддинги
здесь НЕ развиваем — они вынесены в ОТДЕЛЬНУЮ ветку «AI-поиск»
(`docs/ai-search.md`), которая не встраивается в этот поиск, а идёт
параллельно. Смысловая близость, поля, векторный rerank — там, не тут.
Опечаточный trigram-fuzzy по русским переводам — **вне скоупа** (см. ниже).

Два документа, две ветки:
- ЭТОТ — лексический поиск (буквы, слова, формы, синонимы-соседи).
- `docs/ai-search.md` — семантический AI-поиск (смысловые поля, эмбеддинги).
- Приоритеты всех веток: `docs/plans/INDEX.md`.

Как запускать тесты: `docker exec -i -w /app punzh_django python manage.py test dict`
(`-w /app` обязателен: без него модули резолвятся как `app.dict.*` → app_label).
Диагностические скрипты: `docker exec -i punzh_django python manage.py shell < app/<файл>.py`
и ТОЛЬКО плоский код — без функций верхнего уровня и без comprehensions
(оба не видят имён скрипта под exec()).

## ПРИОРИТЕТ 1 — стоп-токены в token-OR (вариант A)

**План:** `docs/plans/search-query-stopwords.md`.

**Проблема.** Многословный запрос → OR по каждому токену. «о корове» / «при …»
раздувают выдачу служебным словом. `STOPWORDS` сейчас только для ключей `?f=`.

**Идея.** При ≥2 токенах в OR не участвуют стопы (1a∪1b∪1c). Однословники
и «вон там» не ломать. Список 1c — из `audit_query_stopwords` + ручной отбор.

**Зацепка.** `rus_search_core` → `_translate_q_any_query_token` / фильтр
`_query_tokens`; тесты рядом с `test_search_token_regression`, `test_search_korova`.

## ПРИНЯТОЕ РЕШЕНИЕ (2026-09) — морфология без FTS и без русского trigram

**Направление.** Русский лексический поиск развиваем через **лемматизацию
токенов с обеих сторон** (запрос и `rus_word`), не через Postgres FTS и не
через trigram.

**Почему не FTS / `search_vector`.** Поле `ArticleIndexTranslate.search_vector`
пишется (`simple`), но **не читается** поиском. Baseline сознательно:
ILIKE + token-OR, не FTS `russian`. Snowball не закрывает глагольную морфологию
и размывает контракт `?f=exact`. Возврат к FTS — только отдельное решение
(например ranking / взвешенный индекс с keywords), не фикс падежей.

**Почему не trigram (бывший P2).** В поиске с русского боль — падеж, число,
формы в переводах, не опечатки вроде `говрить`. Trigram остаётся у
**карельской** ветки (`search_possible` / нормализации). Русский P2 —
**снят со скоупа** (не делать).

**Инвариант данных.** В `rus_word` часто **не** словарная форма: `(о корове)`,
мн. число, падеж во фразе. Лемматизировать только запрос недостаточно —
нужен общий ключ сравнения и для токенов перевода (на лету или колонка при
записи индекса).

**Контракт после внедрения:**

| Слой | Правило |
|------|---------|
| Token-OR / полная выдача | совпадение по **лемме** токена (сюда уходит роль one-letter fuzzy) |
| `?f=exact` | по-прежнему **поверхность** `rus_word` = запрос (после ё→е); эталон «корова»/1717 не размывать |
| Сужающие теги | вычитать из кандидата токены с той же леммой, что у запроса |

**Сейчас в коде.** Временный суррогат: fuzzy «основа без последней буквы»
(`_token_boundary_fuzzy_regex`, len ≥ 5) — `корова`↔`корове`. Снять после
лемм.

## ПРИОРИТЕТ 3 — Лемматизация токенов (запрос + перевод)

**Проблема.**

1. Token-OR и exact-вычитание в ярлыках — по **поверхности**, поэтому
   `корова`↔`корове` ловится только хрупким fuzzy; `быстрый/быстрее` при
   запросе `быстро` торчат в тегах и не сходятся по лемме.
2. Переводы в индексе часто не в словарной форме — см. решение выше.

**Решение.** Лемма (или стабильный stem) токенов запроса **и** токенов
`rus_word`. Предпочтительно: нормализованный ключ при записи индекса
(колонка / поле рядом с `rus_word`); pymorphy или эквивалент. Суррогат
`startswith(query[:N])` — только как дешёвый эксперимент, не целевой контракт.

После внедрения: убрать `_token_boundary_fuzzy_regex` из token-OR; переписать
`test_query_form_variant_leaks_into_label` и эталон «корова» (полная выдача
без опоры на one-letter fuzzy).

**Не делать здесь:** FTS/`search_vector`; trigram по `rus_word`; смена
семантики `?f=exact` на лемма-равенство целой строки.

**Зацепка.** `rus_search_core` / `_translate_q_any_query_token`; запись
индекса (`translation_index_write`, signal); тесты `test_search_korova`,
`test_search_token_regression`, `test_split_by_coverage`.

## ПРИОРИТЕТ 4 — keywords: лексика иллюстраций  [новое, дёшево]

**Идея.** LLM-классификатор (ветка AI-поиска) попутно извлёк русские ключевые
слова из ВСЕЙ карточки, включая ИЛЛЮСТРАЦИИ и толкования — лексику, которой нет
в переводах (`rus_word`) и которую классический поиск сейчас НЕ находит.
Пример: «рыжики» в статье `s'ien'i` (в переводах только «гриб/волнушка»).

**Почему это ЛЕКСИЧЕСКИЙ пункт (сюда, не в AI).** Это точный поиск СЛОВА, не
смысловая близость. keywords вливаются в русский поиск как доп. индекс (с
меньшим весом — они шумноваты). Вскрывают запертую в `article_html` лексику
иллюстраций — старый блокер «по иллюстрациям не искать» частично снят.

**Статус.** Данные уже собираются (в `classified_all.json`), модель
`ArticleKeyword` и команда `load_keywords` готовы. Осталось: чистка от шума
(стоп-слова/POS, программная — НЕ LLM) + подмешать в русский поиск.
Детали модели — `ArticleKeyword`; чистка шума и подмешивание в `/search/` — этот пункт, не AI-поиск.

## МЕЛОЧИ / ТЕХ-ДОЛГ

- **Схлопывание почти-дублей.** Многословные ключи дают близкие теги
  (`ехать` и `ехать лошади`). Дедуп по точному ключу их не схлопывает.
  Рассмотреть схлопывание вложенных ключей.
- **Покрытие по подстроке.** `лес` матчит `лесной`. Взято для согласованности с
  диагностикой; если всплывёт шум — заменить на токен-точное совпадение.
- **«Слишком общие» ключи.** `делать` (16/81) и т.п. — в **начале** списка
  (широкие теги выше). Потолок НЕ вводим — нет данных обосновать порог
  (решение принято сознательно).
- **Косметика кнопки «Точные».** Была жёлтой (`warning`) — плохо читалась на
  белом, сейчас `btn-info`. Довести вид.
- **Правило ярлыка.** Сейчас вариант A (все стоп-слова видны, включая `что-л`,
  ведущее `и`). Обсуждались B/C/D/E — если мусор в ярлыках мешает, вернуться к
  варианту D (пометы везде + союзы/предлоги по краям).

## ПРИНЯТЫЕ ОГРАНИЧЕНИЯ (не баги, не «чинить по умолчанию»)

- Морфоварианты запроса просачиваются в ярлык, пока нет P3 (леммы).
- One-letter fuzzy в token-OR — временный суррогат до P3.
- `search_vector` пишется, поиском не используется — не чистить «заодно» без задачи.
- Наследование прямоты — ОДИН хоп, связи только внутри выдачи.
- Кривой ввод перевода (`ropšata`: фраза, порезанная в осколки) принимается
  как есть — дефект данных, не алгоритма.
- Состояние «свёрнуто/развёрнуто» блока подсказок не переживает пагинацию
  (Bootstrap collapse в DOM, не в URL) — по умолчанию свёрнут.

## УРОКИ ИНФРАСТРУКТУРЫ (чтобы не наступить снова)

- Диагностические скрипты под `manage.py shell < file` — ТОЛЬКО плоский код
  (без функций верхнего уровня и без comprehensions; оба создают свой скоуп и
  не видят имён скрипта под exec()).
- Тесты запускать с `-w /app` (иначе `__init__.py`-артефакты дают `app.dict.*`
  и ошибки app_label). В `/app/__init__.py` быть не должно.
- Когда правка «в несколько строк» дважды теряется — просить/отдавать ФАЙЛ
  ЦЕЛИКОМ, не фрагмент. Одинаковый вывод теста при повторном прогоне = код на
  диске не менялся (файл не тот / правка не доехала).
-
