## ГРАНИЦА: это ЛЕКСИЧЕСКИЙ поиск, НЕ семантика

Документ — про «классический» поиск: точное/подстрочное совпадение, синонимия
по соседству в статье, fuzzy по написанию, морфоформы. Семантику и эмбеддинги
здесь НЕ развиваем — они вынесены в ОТДЕЛЬНУЮ ветку «AI-поиск»
(`docs/CONCEPT_ai_search.md`), которая не встраивается в этот поиск, а идёт
параллельно. Смысловая близость, поля, векторный rerank — там, не тут.

Два документа, две ветки:
- ЭТОТ — лексический поиск (буквы, слова, формы, синонимы-соседи).
- `CONCEPT_ai_search.md` — семантический AI-поиск (смысловые поля, эмбеддинги).

Как запускать тесты: `docker exec -i -w /app punzh_django python manage.py test`
(`-w /app` обязателен: без него модули резолвятся как `app.dict.*` → app_label).
Диагностические скрипты: `docker exec -i punzh_django python manage.py shell < app/<файл>.py`
и ТОЛЬКО плоский код — без функций верхнего уровня и без comprehensions

## ПРИОРИТЕТ 1 — «Связанные запросы» через синонимию  [ближайшее, дёшево]

**Идея.** Прямое попадание `ruttoh` имеет односложные переводы `быстро, круто,
скоро`. `круто`/`скоро` — ДРУГИЕ русские слова, у них свои карельские статьи ВНЕ
выдачи «быстро». Значит через синонимы прямых попаданий выходим на «связанные
запросы» — настоящие переходы наружу, БЕЗ pgvector.

**Почему это закрывает старую дыру.** Мы доказали (SPEC v3 Прил. A): переходов в
лексике нет, т.к. кандидаты = подмножество выдачи. Синонимы прямых — исключение:
они приходят из графа синонимии внутри статьи, а не из фултекста → ведут наружу.

**Зацепка в коде.** `find_direct_hits` уже группирует переводы по статье
(`blobs_by_article`). Расширить: для каждого прямого попадания взять его
односложные переводы, вычесть слова запроса → это и есть связанные запросы. Клик
= новый поиск по синониму (`/search/<синоним>`).

**Границы / решения.** Это ЛЕКСИЧЕСКАЯ синонимия «по соседству в статье», НЕ
смысловая близость (смысловая — в AI-поиске). Качество зависит от того,
насколько односложные переводы одной статьи синонимичны (обычно да — лексикограф
группирует). Риск: далёкое значение среди синонимов (напр. `ruttoh` даёт ещё
«неожиданно» в примере с `kuol’i`). Отдельный блок UI, семантика клика = переход.

**Данные (из прогона «быстро»):** прямых статей с >1 синонимом — 12 из 12.
Материал есть.

**Критерий готовности.** Отдельная функция `find_related_queries(...)` (чистая,
тестируемая на dict), отдельный блок в шаблоне, клик уводит на новый запрос.

## ПРИОРИТЕТ 2 — Механизм 2: спасение запроса (fuzzy) на пустой выдаче

**Идея.** Когда `found_count == 0` (пользователь промахнулся формой/опечатался):
`TrigramSimilarity("rus_word", query) > 0.3` → близкие по написанию переводы.

**Проверено (SPEC v3 Прил. B):** `говрить→говорить`, `кошку→кошка` работают.
`идёт→идти` НЕ находится (словоизменение — граница метода, нужен стеммер).

**Важно.** НЕ переиспользовать `search_possible` — он ищет по
`ArticleIndexWordNormalization` (карельский латинский индекс), на кириллицу даёт
`[]`. Нужна отдельная ветка по `rus_word` (русскому полю).

**Зацепка.** Новая ветка в `search()`/`search_by_translate_linked` при пустой
выдаче, по образцу карельской `if not len(page_obj.object_list)`.

## ПРИОРИТЕТ 3 — Стеммер морфоформ  [чинит сразу две проблемы]

**Проблема.** Вычитание слов запроса — ТОЧНОЕ (`query_words`), поэтому
`быстрый/быстрее` при запросе `быстро` (а) торчат мусором в тегах и (б) НЕ
попадают в точные соответствия. Обе беды — одна причина.

**Решение.** Вычитать по основе, а не точно. Варианты: pymorphy (точно, тяжёлая
зависимость) или суррогат `token.startswith(query[:N])` (дёшево). На данных
префикс `быстр`/`быст` добавлял 4 формы БЕЗ ложных срабатываний; длину мерить
на данных.

**Зафиксировано.** Утечка формы в ярлык покрыта тестом
`test_query_form_variant_leaks_into_label` — при внедрении стеммера его переписать.

## ПРИОРИТЕТ 4 — keywords: лексика иллюстраций  [новое, дёшево]

**Идея.** LLM-классификатор (ветка AI-поиска) попутно извлёк русские ключевые
слова из ВСЕЙ карточки, включая ИЛЛЮСТРАЦИИ и толкования — лексику, которой нет
в переводах (`rus_word`) и которую классический поиск сейчас НЕ находит.
Пример: «рыжики» в статье `s'ien'i` (в переводах только «гриб/волнушка»).

**Почему это ЛЕКСИЧЕСКИЙ пункт (сюда, не в AI).** Это точный поиск СЛОВА, не
смысловая близость. keywords вливаются в русский поиск как доп. индекс (с
меньшим весом — они шумноваты). Вскрывают запертую в `article_html` лексику
иллюстраций — старый блокер «по иллюстрациям не искать» частично снят.

**Статус.** Данные уже собираются (в `classified_all.json`), модель
`ArticleKeyword` и команда `load_keywords` готовы. Осталось: чистка от шума
(стоп-слова/POS, программная — НЕ LLM) + подмешать в русский поиск.
Полное описание — `docs/BACKLOG_keywords_search.md`.

## СЕМАНТИКА / ЭМБЕДДИНГИ — НЕ ЗДЕСЬ

Раньше тут был «Приоритет 4 — pgvector, семантические соседи». ПЕРЕНЕСЕНО в

семантику НЕ развиваем. Не делать pgvector дважды.

## МЕЛОЧИ / ТЕХ-ДОЛГ

- **Схлопывание почти-дублей.** Многословные ключи дают близкие теги
  (`ехать` и `ехать лошади`). Дедуп по точному ключу их не схлопывает.
  Рассмотреть схлопывание вложенных ключей.
- **Покрытие по подстроке.** `лес` матчит `лесной`. Взято для согласованности с
  диагностикой; если всплывёт шум — заменить на токен-точное совпадение.
- **«Слишком общие» ключи.** `делать` (16/81) и т.п. Пока просто в хвосте
  сортировки по покрытию. Потолок НЕ вводим — нет данных обосновать порог
  (решение принято сознательно).
- **Косметика кнопки «Точные».** Была жёлтой (`warning`) — плохо читалась на
  белом, сейчас `btn-info`. Довести вид.
- **Правило ярлыка.** Сейчас вариант A (все стоп-слова видны, включая `что-л`,

## ПРИНЯТЫЕ ОГРАНИЧЕНИЯ (не баги, не «чинить по умолчанию»)

- Морфоварианты запроса просачиваются в ярлык (см. Приоритет 3).
- Наследование прямоты — ОДИН хоп, связи только внутри выдачи.
- Кривой ввод перевода (`ropšata`: фраза, порезанная в осколки) принимается
  как есть — дефект данных, не алгоритма.
- Состояние «свёрнуто/развёрнуто» блока подсказок не переживает пагинацию
  (Bootstrap collapse в DOM, не в URL) — по умолчанию свёрнут.
